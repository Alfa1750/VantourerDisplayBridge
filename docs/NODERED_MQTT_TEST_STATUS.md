## Confirmed duplicate-message cause — overlapping MQTT subscriptions (2026-11-24)

A duplicate-output problem was reproduced and resolved in the `mqtt test` flow:

- The intended MQTT Input node `alle accus` subscribed to the exact topic `N/b827eb14d4ec/system/0/Batteries`.
- A second MQTT Input node, `Camper-Pi MQTT – Testdata`, used the wildcard subscription `N/+/system/0/#` and the same reusable MQTT broker configuration.
- The wildcard subscription also matches `N/b827eb14d4ec/system/0/Batteries`: `+` matches the portal/device segment and `#` matches the remaining path, including `system/0/Batteries`.
- With both MQTT Input nodes enabled, the same battery inventory appeared twice in Debug at the same timestamp with identical payload values but different Node-RED `msg._msgid` values. This showed two separately-created Node-RED messages; by itself, different `_msgid` values do not prove that Venus OS published twice.
- The user disabled `Camper-Pi MQTT – Testdata` (the node was retained, not deleted) and deployed the flow.
- After that change, the `alle accus` path produced one message approximately every five seconds. The user confirmed the duplicate output was gone.

**Future troubleshooting rule:** when an MQTT Input/Debug path produces identical outputs more than once, inspect every enabled MQTT Input node using the same broker configuration and look for overlapping exact and wildcard topic filters (`+` and `#`). Do not assume that different `msg._msgid` values mean the publisher sent duplicate publications. Temporarily disabling the suspected overlapping subscription is a useful controlled confirmation; retain the node until its purpose is reviewed.

This is a confirmed cause for this specific flow and configuration. It does not mean every duplicate MQTT message is necessarily caused by overlapping subscriptions; check the actual topic filters and reproduce the result before changing a flow.

## Agreed data-processing design

Use **one MQTT Input** subscribed to:

`N/b827eb14d4ec/system/0/Batteries`

Feed it into **one Function node** that parses `msg.payload.value` and normalizes the relevant battery entries by stable identity (prefer `instance` and/or the service `id`, not array position or display name).

The Function output should include only:
- Shunt 1 / instance 293: voltage, current, power, SOC.
- Shunt 2 / instance 294: voltage, current, power, SOC.
- Starter battery: voltage.

Do not include the USB-connected JK BMS entry in this MQTT display-data Function. The JK BMS devices are to be disconnected from USB and read separately by a future Raspberry Pi BLE monitor that reads both JK BMS batteries directly over BLE. That monitor is a separate component/repository and will forward its own telemetry to Node-RED. Do not route JK BMS data through the SmartShunt MQTT normalization.

The Function should tolerate missing fields and should not silently substitute zero for unavailable values. The exact output JSON schema, timestamps/freshness policy, and downstream TCP message schema are not yet implemented or accepted.

## Intended deployment portability

The same MQTT Input + Function design is intended to work in both locations:
- **Home testing:** test Pi connects remotely to the camper Pi broker at `192.168.1.113:8883` using its paired token.
- **Final camper deployment:** Node-RED runs on the camper Pi and uses its local Venus OS MQTT broker configuration (the user expects to select the local broker, rather than use the remote address).

The local broker selector/port/TLS details must be verified on the camper Pi before final deployment. Do not assume that the remote TLS settings can simply be copied unchanged to the local broker.

- The Inject node is not required for the recurring battery messages observed here. The user disconnected Inject and confirmed the MQTT messages continued about every five seconds.
- The two wildcard MQTT Input nodes for instances 293 and 294 already exist in the user's flow. Do not ask the user to recreate them.
- The JK BMS USB entry is temporary and must be excluded from this MQTT processing path.
- A previous proposed direct read request using `R/<portal-id>/battery/<instance>/Soc` was not verified. Do not treat that request as a confirmed way to retrieve SOC or consumed Ah.
